[BASE-AGENT] 适配方案对比

方案 A（推荐起步）：[BASE-AGENT] 原生主循环 + 薄 FastAPI shim

优势：

  • 完全保留 [BASE-AGENT] 原生 loop / 工具 / skills / 自进化，[BASE-AGENT] 是真正底座
  • 不要求 [BASE-AGENT] 继承 LlmAgent/BaseAgent，绕开类型不兼容
  • Runtime 侧须满足三层契约：层1 强制（端口/启动命令/健康检查存在/鉴权 KeyAuth 或 JWT/资源网络 IAM）；层2 可选 [BASE-ADK] 路由（/run /run_sse /sessions /ping）；层3 [DELIVERY] 自研 shim 逻辑

代价：

  • 需自实现 Runtime HTTP 协议（鉴权 header / SSE 事件 / session 语义）
  • [BASE-AGENT] state.db 会话模型与 Runtime session 模型需对齐

方案 B：[BASE-AGENT] 包成类 BaseAgent wrapper，复用 [BASE-ADK]

优势：

  • 零手写 Runtime 协议，白捡 [BASE-ADK] 的 HTTP/SSE/鉴权/session 全套
  • 可被 ADK 编排（Sequential/Parallel/Loop/Supervisor）包裹
  • harness_extension 接口极窄（仅 sidecar_status_payload + close）

代价：

  • 需把 AIAgent turn 语义翻译成 ADK Runner event stream（主要工程量）
  • 耦合 [BASE-ADK] 版本（[PRODUCT]-sdk-python≥0.8.2 才支持 identity）
  • BaseAgent 抽象方法清单未读，wrapper 边界待补

注：方案 C「[BASE-ADK] 主 + [BASE-AGENT] MCP sidecar」不符合原需求约束（[BASE-AGENT]为底座），不采用此方案——它把底座让给 [BASE-ADK]，[BASE-AGENT] 退化为工具提供方，违背「[BASE-AGENT] 是 [DELIVERY] 底座」要求。且 [BASE-AGENT] mcp_serve.py 是 messaging bridge（10 个工具：会话/历史/事件/审批/出站消息），不是完整 agent loop，不能当「发 prompt→跑 loop→回答案」的 RPC。
