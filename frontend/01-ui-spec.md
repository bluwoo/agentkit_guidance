# AgentKit Agent 开发 Wizard —— 前端 UI 规格（01）

> 文档性质：**设计规格（Design Spec），不是可运行前端代码**。本文只描述界面布局、组件与交互行为；所有"接通观测 / 评测 / Runtime"的表述在当前阶段均为**设计目标**，不代表已实现。
> 证据来源：`docs/hermes-veadk/05-hermes-as-base-verification.md`（Wizard 底座 = Hermes Agent `AIAgent.run_conversation` + 薄 FastAPI shim，非 veADK Agent）、`docs/volcengine-official/shard4-results.md`（观测：已核验日志字段仅 10 个；**埋点字段/完整 trace span 契约未获取**）、`shard1-results.md`/`shard2-results.md`（AgentKit Runtime API）、`15-evaluation.md`（评测三件套）、`docs/lark-supplements/doc07.md`（观测评测 GTM、trace 回流、trace 数据真实性约束）、`docs/volcengine-official/00-directory.md`（组件清单）。
>
> **修订基线（2026-09-18）**：① Wizard 后端为 Hermes 原生主循环 + 薄 FastAPI shim，不是 veADK Agent；② Trace 覆盖层数据契约仅基于**已核验的 10 个日志字段 + trace_id**，完整 span 字段契约待 APMPlus/VeADK 文档站核验，当前为设计假设；③ 本阶段未执行云联调，火山引擎凭据可用性尚未核验，所有接口均为设计目标。

---

## 0. 设计原则

1. **引导式开发（Guided）**：每一步明确告诉用户"现在需要什么输入、为什么需要、下一步去哪"，默认走最合理路径。
2. **设计时 ≠ 运行时**：架构图表达的是用户**设计的连接拓扑**；trace 覆盖层表达的是**真实发生的调用**。二者用不同视觉编码（见 `02-architecture-diagram-spec.md`）。
3. **数据真实性优先**：trace / 评测数据只允许来自观测 API 与评测服务的真实返回；无数据、未接通时必须显式显示"无观测数据 / 服务未配置"，**禁止编造调用关系**（依据 doc07：trace 数据来自 APMPlus trace API，Follow gen.ai 语义；doc07 友商对比中"无 trace 自动回流"即为反面案例）。
4. **可编辑草稿**：每一步产出都是结构化、可二次编辑的文档/配置，而非只读结论。

## 1. 整体信息架构与导航

### 1.1 顶部步骤条（Stepper）

固定在页面顶部，4 个步骤 + 1 个结果视图：

```
[1 业务目标] → [2 验收与评测] → [3 架构设计] → [4 架构图 + 测试]
```

- 每个步骤节点显示：序号、标题、状态（`待完成 / 进行中 / 已完成 / 有告警`）。
- 已完成步骤可点击回退编辑；回退编辑后若影响下游（如改了业务目标），下游步骤标记为"需复核"（黄色小圆点），但不强制锁死。
- 当前步骤右侧显示"下一步"主按钮；未满足进入条件时按钮置灰并 hover 提示缺什么。

### 1.2 三栏工作区布局（桌面端 ≥1280px）

```
┌─────────────────────────────────────────────────────────────┐
│ Stepper: ①业务目标 ②验收评测 ③架构设计 ④架构图+测试          │
├──────────┬───────────────────────────────────┬─────────────┤
│ 左栏     │  中栏（主工作区，随步骤切换）      │  右栏       │
│ 上下文   │                                   │  上下文/   │
│ 摘要     │                                   │  产物预览  │
│ (Context)│                                   │ (Artifact) │
└──────────┴───────────────────────────────────┴─────────────┘
```

- **左栏 Context**：常驻显示"本 Wizard 已确认的业务目标要点 + 验收标准摘要"，让用户在任意步骤都能看到上下文，避免迷失。
- **中栏**：当前步骤的主操作区。
- **右栏 Artifact**：当前步骤的结构化产物（业务目标文档 / 验收用例表 / 组件配置），可折叠、可复制、可导出。

### 1.3 导航状态

- 每步有独立 URL 路由（如 `/wizard/biz-goal`、`/wizard/evaluation`、`/wizard/architecture`、`/wizard/diagram-test`），支持刷新保留、分享链接。
- 左侧 Context 摘要随步骤自动同步后端已保存草稿。

## 2. Step 1：业务目标确定

### 2.1 顶部路径切换（两种模式互斥切换）

中栏顶部放一个 Segmented Control：

```
( ● 深度访谈 grill-with-docs   )  (   快速生成 prompt   )
```

- 切换时若已有内容，弹窗提示"切换模式将保留已确认要点但重置当前输入"。

### 2.2 模式 A：grill-with-docs 深度访谈

> **前置事实（据 05 核验 §6）**：`grill-with-docs` 是**纯 prompt/流程型 skill**，自身无代码、无依赖，`disable-model-invocation: true` 且 `allow_implicit_invocation: false` —— **不能被模型隐式自动触发，必须显式调用**。用户在 Step1 选择该模式并点击"开始访谈"后，Wizard 才显式启动该流程；流程内部**依次调用 `grilling` 与 `domain-modeling` 两个子 skill**，并在过程中产出 ADR 与 glossary。它不绑定特定运行时，只要宿主（Hermes）支持按名调用子 skill + 写文档即可。

**布局：左右分栏（对话 | 已确认要点）**

```
┌────────────────────────────┬───────────────────────────┐
│  对话区（Chat）            │  已确认要点（右侧实时同步）│
│  ┌──────────────────────┐  │  ✓ 目标用户：企业客服     │
│  │ Wizard 提问气泡      │  │  ✓ 核心任务：工单分类     │
│  │ 用户回答气泡         │  │  ✓ 非目标：不做退款操作   │
│  │ Wizard 追问...       │  │  ...                     │
│  └──────────────────────┘  │  [生成 ADR] [术语表]      │
│  输入框 + 发送              │                           │
└────────────────────────────┴───────────────────────────┘
```

**交互要点：**
- 用户选择"深度访谈 grill-with-docs"模式后，需点击**显式启动**按钮才进入访谈（该 skill 不自动触发）。
- 访谈阶段（对应子 skill `grilling`）：Wizard 以**追问式**提问，一次聚焦一个点（如"这个 Agent 主要服务谁？""成功长什么样？""有哪些明确不做的事？"），不一次性倒出大段问卷。
- 用户回答后，Wizard 自动抽取要点，**经用户确认**后才写入右侧"已确认要点"清单（每条带勾选态，可删除/改措辞）。
- 要点沉淀阶段（对应子 skill `domain-modeling`）：右侧清单下方两个动作：
  - **生成 ADR（Architecture Decision Record）**：把已确认的关键取舍生成结构化决策记录草稿。
  - **生成术语表（Glossary）**：抽取访谈中出现的业务术语，形成术语表草稿。
- 底部"下一步：定义验收标准"按钮，在已确认要点 ≥1 条后可用。

### 2.3 模式 B：prompt 快速生成

**布局：表单 + 自由文本**

```
┌───────────────────────────────────────────┐
│ Agent 名称：[____________]               │
│ 一句话描述这个 Agent 要做什么：          │
│ [ 多行文本输入框 / 占位："帮企业客服..."] │
│ 服务对象：[下拉/多选]  主要语言：[下拉] │
│ 期望调用的外部系统（选填）：[标签输入]   │
│                                           │
│ [ 生成业务目标草稿 ] （调用后端生成）     │
├───────────────────────────────────────────┤
│ 生成的业务目标文档（可编辑 Markdown）    │
│ # 业务目标草稿 ...                        │
│ [ 采纳为正式产物 ]  [ 重新生成 ]         │
└───────────────────────────────────────────┘
```

### 2.4 产出（右栏 Artifact）

结构化业务目标文档：`{ 名称, 目标用户, 核心任务, 成功标准, 非目标, 术语表, ADR[] }`，全部可编辑。

## 3. Step 2：验收标准与评测

### 3.1 验收标准模板引导

中栏顶部说明条（**关键提示，固定展示**）：

> 💡 验收标准要描述"**实际产物/外部状态的变化**"，而不是"Agent 说它完成了"。判断的是结果，不是 Agent 的完成声明。
> （依据 15-evaluation.md：评测关注效果/性能/成本三方面真实结果；doc07：bad case 靠 trace 真实回流沉淀。）

逐条添加验收用例卡片，每个用例表单字段：

| 字段 | 说明 |
|---|---|
| 输入 | 给 Agent 的 prompt / 多模态输入 |
| 预期输出 | 期望的产物（文本/文件/结构化字段） |
| 判断方式 | 四选一（见 3.2） |
| 边界 case | 明确"不应该发生"的反例（如不该执行退款） |

列表支持增删、拖拽排序、从右栏导出为 JSON/CSV（对接评测集）。

### 3.2 评测判断方式选择（每个用例可选）

单选/多选，卡片 radio：

- **独立产物验证**：检查 Agent 产出的文件/数据本身是否满足 schema/断言。
- **外部状态检查**：检查调用后外部系统状态是否真的变化（如工单是否真的被创建，而非 Agent 声称创建）。
- **LLM-as-Judge**：由评估模型对结果打分（依据 15-evaluation.md：自动化评估器 / LLM 评估打标；doc07：内置官方评估器 + LLM-as-Judge）。
- **人工校准**：人工复核打标（doc07：LLM-as-Judge 与人工校准并行）。

### 3.3 评测集管理界面

- **关联 AgentKit 评测服务**的入口（设计目标，当前未接通）：一个"绑定评测集"下拉，显示"当前未连接评测服务"占位态，不假装已拉到数据。
- 本地可先维护用例表（即 3.1），标注每条用例的"判断方式"，待评测服务接通后可一键导入为评测集条目。
- 顶部提示："线上真实 trace 可回流为评测集 good/bad case（依据 doc07 数据回流能力）"——作为引导文案，不展示假数据。

## 4. Step 3：架构设计

### 4.1 三栏工作区

```
┌──────────────┬─────────────────────────────┬──────────────┐
│ 左：组件面板 │  中：画布（拖拽式连接编辑）│ 右：配置面板 │
│ (14 组件卡片)│                             │ (选中组件后) │
│ 智能推荐区   │                             │              │
└──────────────┴─────────────────────────────┴──────────────┘
```

### 4.2 左栏：组件选择面板

**智能推荐区（顶部）**：基于 Step1 业务目标 + Step2 验收标准，后端给出推荐组件组合，以"推荐"角标卡片呈现；用户可一键"采纳推荐"铺到画布。推荐为空时显示"暂无足够信息，请先补全业务目标"，不硬塞。

**组件卡片库**：按 `00-directory.md` 的组件清单分组成可拖拽卡片，每张卡片显示：

- 组件名称 + 一句话用途（如 知识库=VikingDB RAG 语义检索）
- **前置条件**（来自对应 Skill 的前置要求，如"需先创建知识库资源"）
- **所需权限**（如出站访问火山资源、私网域名）

组件分组（对应 00-directory.md 章节）：
Runtime / 沙箱 Sandbox(工具) / Skills / A2A Registry / 会话与记忆 Session&Memory / 知识库 KnowledgeBase / 网关 Gateway / MCP 服务与工具集 / 身份与权限 Identity / 安全围栏 Guardrails / 观测 Observability / 评测 Evaluation / 模型服务 / 函数服务。

### 4.3 中栏：连接关系编辑（画布）

- 从左栏**拖组件到画布**生成节点。
- **拖拽连线**：从一个节点的连接点拖到另一个节点，建立"调用/数据流"边（如 Agent → 工具 → 知识库 → MCP → 网关）。
- 节点可移动、对齐、删除；边可删除；双击边可改边类型（同步/异步/数据流/配置依赖，见 `02`）。
- 右上角工具条：自动布局 / 缩放 / 撤销重做 / 清空。

### 4.4 右栏：配置面板

选中画布中某组件节点后，右栏显示该组件的配置项：

- 配置项**来源于对应 Skill 的前置条件与环境变量**（如 Runtime 的镜像/模型配置/环境变量；知识库的私网访问配置；MCP 的后端服务/入站认证）。
- 字段分"必填 / 选填"；必填未填时节点在画布上显示**橙色缺配角标**。
- 面板底部放"查看对应 Skill 文档"链接（指向该组件 Skill 的说明，不伪造内容）。

### 4.5 实时校验（画布顶部横条）

实时校验并以横条展示问题清单：

- 组件**依赖缺失**（如连了知识库但没选 KnowledgeBase 节点）
- **权限缺失**（如 MCP 出站访问未配权限）
- **配置不完整**（必填环境变量为空）

问题可点击定位到对应节点；全部通过后显示绿色"架构校验通过"，才允许进入 Step 4。

## 5. Step 4：架构图 + 测试验证

> 这是本 Wizard 的核心视图。架构图为**可交互拓扑**（非静态图片），测试与 trace 覆盖层叠加其上。详见 `02-architecture-diagram-spec.md`。

### 5.1 布局

```
┌───────────────────────────────────────┬──────────────────┐
│  上：可交互架构拓扑图                  │ 右：测试面板      │
│   (设计时拓扑 + 可选 trace 覆盖层)     │                  │
│   节点可点击 → 显示配置详情/Skill      │  测试 prompt 输入 │
│                                       │  user_id/session │
│                                       │  [发送 /invoke]   │
│                                       │  响应流(SSE)      │
├───────────────────────────────────────┴──────────────────┤
│  下：Trace 覆盖层开关 + 图例 + 节点详情抽屉               │
└──────────────────────────────────────────────────────────┘
```

### 5.2 架构图交互

- **节点类型**：Agent / Skill / MCP 服务 / 知识库 / 沙箱 / 网关 / Runtime / 记忆库 等（视觉编码见 `02`）。
- **边**：调用关系 / 数据流。
- **缩放 / 拖拽平移 / 框选**；**点击节点**弹出抽屉显示该节点的配置详情与对应 Skill 链接。
- 顶部一个 **"Trace 覆盖层"开关**（默认关）：开启后叠加运行时真实调用着色（见 5.4）。

### 5.3 测试面板（右栏）

- 输入测试 prompt；选择/填写 `user_id`、`session_id`。
- **测试调用目标**：由用户在 Step3 选定的"目标 Agent / 目标 Runtime"决定。调用路径二选一（设计目标，当前未联调）：
  - **经 Wizard 后端透传**：Wizard 后端（Hermes + 薄 FastAPI shim）把请求转发到目标 Runtime 的 `/invoke`（Runtime HTTP 协议端点，见 `03` §3）；
  - **前端直连目标 Runtime**：在已配置目标 Runtime 鉴权（KeyAuth Header）且浏览器可达时，前端可直接调用目标 Runtime `/invoke`。
- 响应支持两种形态：**同步一次性返回**（目标 Runtime `/invoke` 同步语义）或 **SSE 流式**（目标 Runtime `/run_sse`）逐字渲染；流式时显示"连接中/接收中/完成"状态。
- 测试调用记录显示本次 `trace_id`（若后端观测回传）。

> 注意：Wizard 后端自身也实现 Runtime 协议端点（`/run`、`/run_sse`、`/invoke`、`/ping`），那是 **Wizard 底座对外**的协议表面；测试面板默认打的是**目标 Runtime**，不是 Wizard 自身，二者不可混淆。

### 5.4 Trace 覆盖层（核心约束）

测试完成后，前端**从观测服务拉取本次调用 trace**（依据 shard4 §3/§41：观测开启后提供指标/链路/日志一体化，运行日志投递至 `apmplus-server-log` 主题；`doc07`：trace Follow gen.ai 语义），在拓扑图上着色：

- **绿色** = 该节点本次被调用且成功
- **红色** = 该节点本次被调用但失败
- **灰色** = 设计了连接但本次 trace 中未出现
- **边** 上叠加：调用次数 / 时延 / 错误率
- **点击节点**：抽屉显示该组件本次调用详情（输入 / 输出 / 时延 / trace_id）

**⚠️ 数据契约边界（必须在 UI 与本规格中严格体现）：**
1. **已核验的观测字段仅 10 个日志字段**（shard4 附录A）：`attribute`（含 `container_id`/`instance_id` 等）、`file_line`、`file_name`、`hostname`、`log_level`、`message`、`resource`、`service`、`source`、`trace_id`。前端 Trace 覆盖层的数据结构**当前只可基于这 10 个字段 + `trace_id`** 设计；
2. **埋点字段与完整 trace span 字段契约未获取**（shard4 §40：埋点字段页是导航页，详细字段在 APMPlus/VeADK 独立文档站，本次未能拉到）。因此覆盖层所需的 `span_id`/`parent_span_id`/`duration_ms`/`status`/`attributes.gen_ai` 等字段**均为设计假设，待 APMPlus 文档站核验后方可作为开发契约**；
3. trace 数据**必须**来自观测 API 真实返回；
4. 观测未接通 / 无数据 / 接口报错时，覆盖层区域显示**"无观测数据（观测服务未配置或暂无 trace）"占位**，节点一律保持设计时中性色，**不得**用绿/红/灰伪造任何调用关系；
5. **trace 缺失 ≠ 未调用**：S3 状态（完成但无 trace）只说明"本次观测服务未返回数据"，不能据此判定目标 Agent 没有被调用；
6. 设计时拓扑与运行时 trace **分层显示**，开关切换，不混淆。

## 6. 测试验证流程的 UI 状态机

测试面板 + 覆盖层的状态机（5 态）：

```
            ┌──────────────┐
            │ S0 未测试    │  (空 prompt/未发送，覆盖层不可用)
            └──────┬───────┘
                   │ 点击发送 /invoke
                   ▼
            ┌──────────────┐
            │ S1 测试中    │  (SSE 流式接收中，节点保持设计色)
            └──────┬───────┘
          响应完成   │   响应失败/超时
        ┌──────────┴──────────┐
        ▼                     ▼
┌─────────────────┐   ┌─────────────────┐
│ S2 完成+有trace │   │ S4 测试失败     │
│ 覆盖层可开，     │   │ 红色错误条+错误  │
│ 节点按真实调用   │   │ 信息；覆盖层     │
│ 着色(绿/红/灰)   │   │ 不可用          │
└─────────────────┘   └─────────────────┘
        │
        │ 观测未接通/无trace
        ▼
┌─────────────────┐
│ S3 完成+无trace │  覆盖层开关置灰，
│ 显示"无观测数据"│  节点保持设计中性色
└─────────────────┘
```

| 状态 | 触发 | UI 表现 | 覆盖层 |
|---|---|---|---|
| S0 未测试 | 初始/清空 | 测试面板空，拓扑为纯设计时 | 开关禁用 |
| S1 测试中 | 已发送 /invoke | 响应区流式 loading，进度指示 | 开关禁用 |
| S2 完成+有 trace | 响应完成且观测 API 返回本次 trace | 节点绿/红/灰着色，边上有指标 | 可用 |
| S3 完成+无 trace | 响应完成但观测未配置/无数据/接口报错 | 拓扑保持设计中性色，覆盖层区显示"无观测数据"占位（**仅表示观测无返回，不代表目标 Agent 未被调用**） | 开关置灰并说明原因 |
| S4 测试失败 | /invoke 报错/超时 | 顶部红色错误条，展示错误码与 message | 开关禁用 |
